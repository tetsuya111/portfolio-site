# add-portfolio

引数（`$ARGUMENTS`）で指定したプロジェクトを、ポートフォリオとして追加する。処理の本体は Python 製コマンド [portfolios/portfolio-importer](../../../portfolios/portfolio-importer/README.md) で、このスキルはそれを実行し、結果を確認・仕上げ・報告する。

## 確認のルール

基本は確認せずに進める。次の操作だけは、実行する直前に AskUserQuestion で yes/no を確認する。no なら行わずに続ける。

| 操作 | 理由 |
|---|---|
| `npm install`・`npm ci`・`pip install` など、パッケージを取得する操作 | 外部サイトへのアクセス |
| リポジトリ外のファイルの作成・修正・削除 | このプロジェクト以外のディレクトリの操作 |

コピー元がリポジトリ外にあっても、コマンドはコピー元を**読むだけ**なので確認しない。

## 手順

1. **引数の確認**: `$ARGUMENTS` からプロジェクトのパスと、あれば `--slug`・`--site-url` を取り出す。パスがなければ、直前の会話・開いているファイルから推定する。推定できなければ理由を報告して終了する。
   - `--site-url` が引数にないときは、`portfolio-site/infra/README.md` などにサイトのドメインが書かれていないか探し、なければ付けない（掲載 md の `url` は入らない）。
2. **取り込み**:
   ```bash
   python portfolios/portfolio-importer/add_portfolio.py <パス> [--slug <スラッグ>] [--site-url <URL>]
   ```
   終了コード 1 なら標準エラーの理由を報告して終了する（例: コピー先が既にある → 既に取り込み済みなら `portfolios/<スラッグ>` を指定して再実行してよい）。成功なら標準出力の JSON（`slug`・`projectDir`・`copied`・`frontend`・`backend`・`content`・`warnings`）を読む。
3. **モックの仕上げ**: `frontend.mock` が null でなければそのファイル（`portfolio-site/apps/<スラッグ>/mock/handlers.js`）を読み、`TODO` のハンドラーに応答データを書く。S3 にはバックエンドがないため、配信したフロントエンドはこのモックの応答で動く。
   - 応答の形は、バックエンドの該当ルートの実装（レスポンスのモデル・返り値）と、フロントエンドの API 呼び出しの型から決める。データはデモとして自然な固定値にし、POST は受け取った `req.body` を反映した値を返す。
   - ログイン状態を返す API は、ログイン済みを返す（ページ遷移でのログイン・OAuth はモックで横取りできないため、ログイン画面を出さない）。
   - `APIRouter(prefix=...)`・`include_router(..., prefix=...)`・`app.use("/api", router)` などでパスに前置きがある場合は、雛形のパスに前置きを足す。フロントエンドが呼ぶパスと一致しているかも確かめる。
   - フロントエンドが呼ばない API（OAuth のコールバックなど）のハンドラーは消してよい。
   - 秘密情報（API キー・トークン・実在の個人情報）は書かない（このファイルは公開される）。
   - `fetch` 以外（`XMLHttpRequest`・axios の既定・WebSocket）で通信するフロントエンドは、モックが効かない。その旨を報告に書く。
4. **掲載 md の仕上げ**: `content` が null でなければそのファイルを読み、次だけを直す。
   - プロジェクト内への相対リンク・画像（`./docs/x.md` など）は、サイト上で開けないため、文章に置き換えるか削除する。
   - 見出しが `#` から始まっていれば `##` 以下に下げる。
   - 本文が雛形（「ここにポートフォリオの説明を書く」）のままなら、プロジェクトの README・コードから概要・主な機能・技術構成を書く。
5. **検証**: `portfolio-site/` で `npm test` と `npm run lint` を実行し、出力は失敗箇所だけを確認する（例: `| tail -30`）。失敗したら原因を直す（掲載 md の frontmatter など）。依存が未インストールで実行できない場合は、確認ルールに従う。
6. **作業ログ**: CLAUDE.md の規則に従い `logs/<yyyymmdd_hhMMss>_content_add-portfolio-<スラッグ>.md` に、何を・なぜ取り込んだかを書く。
7. **報告**: 次を箇条書きで示す。コミットはしない（ユーザーに任せる）。
   - 取り込み先（コピーしたか）、作成・更新したファイル
   - フロントエンド: 配信登録したか。しなかった場合はその理由。登録した場合の配信 URL（`<サイトURL>/apps/<スラッグ>/`）
   - モック: `handlers.js` の場所と、書いたハンドラーの一覧。動かない可能性のある画面（ページ遷移でのログイン・`fetch` 以外の通信など）
   - `warnings` の全件と、ユーザーが手で対応すべきこと

## よくある間違い

| 間違い | 正しい扱い |
|---|---|
| バックエンドを動かすため Dockerfile を書く・サーバーを立てる | 書かない。S3 だけで動かすため、モックの応答で置き換える |
| コピー先が既にあるエラーで `portfolios/<スラッグ>` を削除して再実行する | 削除しない。取り込み済みなら `portfolios/<スラッグ>` を指定して再実行する |
| 静的出力できないフロントエンドを `apps.json` に手で登録する | 登録しない（デプロイ全体が止まる）。理由を報告する |
| 既存の掲載 md・`handlers.js` を上書きする | 上書きしない。差分が必要なら報告に書く |
