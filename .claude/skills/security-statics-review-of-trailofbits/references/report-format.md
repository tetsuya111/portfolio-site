# セキュリティレビュー共通: 段階の定義と出力形式

`security-statics-review-of-trailofbits` と `security-infra-review-of-trailofbits` の両方がこのファイルに従う（単一情報源）。

## 段階（深刻度）の定義

各指摘は、次の5段階のうち**ちょうど1つ**に分類する。迷ったときは、根拠が足りない方の段階（例: 要修正か要確認かで迷ったら要確認）にし、理由を書く。

| 段階 | 判定基準 |
|---|---|
| 要修正 | 悪用経路を追跡済みで、本番相当の設定で実害が生じる（秘密情報の漏洩、認証回避、任意コード実行、fail-open など）。リリース前に必ず直す。 |
| 要確認 | 危険なパターンだが、悪用できるかどうかが実行環境・運用・デプロイ設定など、コードの外の事実で決まる。誰に何を確認すればよいかを書く。 |
| 要注意 | 現時点では悪用経路がないが、変更や設定ミス1つで脆弱になる（sharp edge、多層防御の欠如、開発用設定の残置など）。 |
| 参考 | 直接のリスクはないベストプラクティス上の改善点（ハードニング、依存の更新、ログ方針など）。 |
| その他 | 上記に当てはまらないもの。誤検知として除外した候補、スコープ外で未確認の領域、ツールが実行できなかった項目など。 |

## 類似バグ（variant）の扱い

- `variant-analysis` で見つかった同じ根本原因の別箇所は、元の指摘の直下に `類似バグ` として列挙する。独立した指摘として重複して数えない。
- 類似バグの段階が元の指摘と違う場合（例: 片方だけ外部入力が届く）は、個別に段階を付ける。
- 類似バグを探したが見つからなかった場合も「類似バグ: なし（探索範囲: …）」と明記する。

## 出力形式

レビュー結果は次の見出し構成で、この順に出力する。該当がない段階も見出しを残して「該当なし」と書く。

```markdown
# セキュリティレビュー結果（<静的 / インフラ>）

## 前提
- 対象: <パス・ブランチ・コミット>
- 対象外: <除外した範囲とその理由>
- 実行したスキル・ツール: <名前と実行結果（成功 / 失敗 / 未インストールのため手動参照）>
- 想定した脅威モデル: <公開範囲、信頼境界など。推測した場合はそう書く>

## 概要
<全体の評価を2〜4文で。段階ごとの件数表を付ける>

| 段階 | 件数 |
|---|---|
| 要修正 | n |
| 要確認 | n |
| 要注意 | n |
| 参考 | n |
| その他 | n |

## 段階

### 要修正
#### [S-1] <タイトル>
- 場所: [file.ts:42](path/file.ts#L42)
- 検出元: <insecure-defaults / variant-analysis / sharp-edges など>
- 内容: <何が問題か>
- 根拠: <悪用経路の追跡結果。どこから値が来て、どの判断に届くか>
- 対応案: <具体的な修正内容>
- 類似バグ:
  - [file2.ts:10](path/file2.ts#L10) — <違い。段階が違えば明記>

### 要確認
#### [C-1] …（確認先・確認事項を必ず書く）

### 要注意
#### [W-1] …

### 参考
#### [I-1] …

### その他
#### [O-1] …

## 備考
<レビューの限界、実行できなかったツールとその理由、追加で推奨する作業（動的テスト、ペネトレーションテストなど）>

## まとめ
<優先して対応すべき項目を順に3つまで挙げ、次の一手を書く>
```

ID の接頭辞: 要修正 `S`、要確認 `C`、要注意 `W`、参考 `I`、その他 `O`。
