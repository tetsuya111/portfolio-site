# 使用量の見える化と対話履歴の保持 の design.md / tasks.md を作成

## 何を

`.kiro/specs/token-usage-and-history-retention/` に design.md と tasks.md を新規作成した。requirements.md の4ストーリーに対する技術設計と、7つの実装タスクへの分解。

- design.md: 変更点を4つに整理（残量の割合をAPIに追加・確定時のLLM呼び出しの統合・保持期間切れの消去バッチ・上限の5倍化）。DBスキーマの変更はなく、マイグレーションは発生しない。
- tasks.md: タスク1（上限5倍）→ 2・3（残量の表示）→ 5（確定の統合）→ 6・4（保持期間と案内）→ 7（ドキュメント）の順。

## なぜ

要件が確定したため、`.kiro/specs/README.md` の手順3・5に従って設計とタスク分解に進んだ。

## 設計で決めたこと

- **残りの割合の算出はサーバー側**（`usage_summary()` に `remaining_percent` を追加）。切り捨てだが、残りが1以上あるうちは0%にしない（「0%なのに使える」状態を避けるため）。フロントエンドは受け取った値を表示するだけにする。
- **確定は「充足判定 + 要件の抽出」を1回のLLM呼び出しに統合**し、3回 → 2回にする。不足がある場合はサマリー作成を呼ばずに1回で返す。サマリー作成エージェントが `status: error` を返したときは、確定の経路に限り不足項目としての差し戻し（422）をやめて `llm_failed` として扱う（同じ観点の判定を2か所に置かないため）。プレビュー（見積もり・要約DL）の経路は現行どおり。
- **消去のロジックは `clear_conversation()` に一本化**し、バッチ（`chat/retention.py` + 管理コマンド `purge_conversations`）はその呼び出し元に徹する。`Conversation` の行自体は消さない（`get_or_create` で作り直されるだけのため）。誤消去に備えて `--dry-run` を用意する。
- **保持期間は `CONVERSATION_RETENTION_DAYS`（既定30日）** として設定に出し、「1か月」を具体値にした。

## 補足

- requirements.md に残していた「割合の丸め方」「残りが少ないときの扱い」は design.md で決着させた（10%未満で色とテキストの両方を変える）。
- 未解決のまま残したのは「バッチの定期実行をどこに置くか（インフラ待ち）」と「許容する月額の上限」の2点。前者は当面手動実行とし、docs/backend.md の申し送り事項に書く（タスク7）。
