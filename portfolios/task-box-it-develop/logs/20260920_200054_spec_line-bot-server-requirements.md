# LINE BOTサーバーの要件定義を新規作成

## 何を

`.kiro/specs/line-bot-server/requirements.md` を新規作成した。元にしたのは `memo/memo_pushed/LINEのBOTサーバー構築_修正版.md`（元メモと懸念点への回答は同ディレクトリ）。

8つのユーザーストーリーに整理した。

1. Webhookの受信（署名検証、即時200、非同期処理、`webhookEventId` による重複排除、対象外イベントの無視）
2. 機能の呼び出しと契約状態による分岐（クイックリプライ/postback、未契約者は対話不可）
3. ユーザー情報の登録（LIFF優先、名前とメールのみ、`userId` はサーバー側で取得、1アカウント1件で上書き）
4. 契約者との対話（待機メッセージ→Pushで回答、200文字程度のプレーンテキスト、見積もりは別ページへ案内）
5. 会話履歴（直近10往復、最後のやり取りから24時間、本文はログに残さない）
6. メッセージの送信（外部非公開、Push、`X-Line-Retry-Key`、ブロック済みは記録のみ）
7. 準備中の機能の扱い（面談調整・契約する）
8. LLMの費用の歯止め（1ユーザー1日あたりの呼び出し回数の上限）

## なぜ

Webで要件サマリーを送った後の連絡窓口がなく、定型のやり取りが管理者の手作業になっているため。実装より先に仕様を `.kiro/specs/` に置くルール（`.kiro/specs/README.md`）に従った。

## 判断したこと

- slug は `line-bot-server`。Django の `backend/` とは別サービス（Python / FastAPI）として切り出す前提を制約に明記した。
- メモの「設計」に書かれていた内容のうち、振る舞いとして検証できるもの（署名検証、冪等性、通数、文字数など）は受け入れ基準に落とし、技術選定（FastAPI、RQ）は制約・依存関係として記述するに留めた。詳細は design.md で決める。
- メモの未決事項（クイックリプライの表示タイミング）に加えて、LIFFの採否、契約状態の参照方法、LLMの上限値、プロンプトの作成時期、実行環境の5件を未解決事項として挙げた。いずれも design.md に進む前に確認が必要。
- 要件サマリーの6項目や見積もりはLINE側では扱わない（Non-Goals に明記）。
