# LINE BOTサーバーの未解決事項を確定（ベストプラクティスに従って決定）

## 何を

`.kiro/specs/line-bot-server/` の requirements.md / design.md / tasks.md を更新し、未解決事項をすべて解消した。

| 事項 | 決定 | 根拠 |
| --- | --- | --- |
| 実行環境 | 常時起動の `web` + `worker`、マネージドのPostgreSQLとRedis、定期実行はcron。既定はPaaS（Render想定）、VPSでも同じ形を保つ | 設定は環境変数（12factor）、プロセスの種類を分ける、バックアップや更新を自前で持たない。事業者に依存する実装は持ち込まず、Webサイト側のインフラが決まったら寄せられるようにする |
| 契約状態の更新者 | 所有者はBOTのDB。更新手段は管理コマンド `set_contract` のみ。リクエストの処理からは書き込まない | 書き込む場所を1つにする（二重の真実を作らない）。SQL直打ちにしないことで手順とログが残る |
| 対話プロンプトの作成時期 | ファイルが無い・空なら仮の応答。設定フラグは増やさない。実装は先に進め、本番公開はプロンプト完成後 | フラグとファイルの状態が食い違う事故を避ける。外部の成果物待ちで実装を止めない |
| LIFFの利用 | `LIFF_ID` 未設定でも登録が完結することを要件にし、テキスト方式を先に実装。LIFFは設定でき次第そちらを本命に | 外部サービスの設定を実装の前提条件にしない。入力体験の良い方を最終形にする |
| `DAILY_LLM_CALL_LIMIT` | 既定30回/日・ユーザー | 1往復3,000〜6,000トークンの見積もりから30往復で約18万トークン。Webサイト側の上限（300,000トークン/日）の範囲に収まり、相談としては十分な回数 |

あわせて、元メモの未決事項だった「クイックリプライの表示タイミング」を受け入れ基準に格上げした（すべての返信に付ける）。

## なぜ

ユーザーの指示（未解決事項はベストプラクティスに従う）による。いずれも design.md の該当節に理由つきで書き、requirements.md の受け入れ基準・制約に反映した。

## 主な変更箇所

- requirements.md: Non-Goals（契約状態の変更は管理コマンドのみ）、ストーリー2 基準8（全返信にクイックリプライ）、ストーリー3 基準2（LIFFなしでも完結）、ストーリー8 基準1（既定30回）、依存関係・制約、未解決事項は「なし」。
- design.md: 「実行環境」の節を新設。契約状態の所有者と `set_contract`、プロンプトのフォールバック、LIFFの位置づけ、上限値の根拠を追記。未解決事項は決定一覧に置き換え。
- tasks.md: タスク2に `set_contract`、タスク7にプロンプトのフォールバック、タスク12にデプロイ構成と cron の手順を追加。

## 残していること

リッチメニューとの併用、契約ページができた後の契約状態の持ち方は、それぞれ別specで扱う（本specの範囲外）。
