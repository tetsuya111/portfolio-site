# 上限の引き上げを取りやめ、管理者の無制限化とファイルによる管理者識別に差し替え

## 何を

`.kiro/specs/token-usage-and-history-retention/` の requirements.md / design.md / tasks.md を更新した。

- **ストーリー4を差し替え**: 「1日の使用量の上限を5倍にする」→「管理者の使用量を無制限にする」。依頼者向けの上限は現行の300,000トークン / 日から変更しない。
- **ストーリー5を新設**: テキストファイル（Googleアカウントのメールアドレスの一覧）による管理者の識別。
- design.md に、管理者の判定（`accounts/admins.py`、`ADMIN_EMAILS_FILE`、ログイン時の `User.role` への同期、`sync_admins` コマンド）と、`ensure_within_limit()` / `usage_summary()` の管理者向けの扱い（`unlimited`）を追加した。
- tasks.md を7タスクから8タスクに再編した（タスク1: 管理者の識別、タスク2: 上限の対象外化、タスク3: 使用量API、以降は既存のタスクを繰り下げ）。

## なぜ

ユーザーからの指示（上限は変更しない / 管理者は無制限 / 管理者はテキストファイルのメールアドレスで識別する）による。requirements.md は「デザインとタスクを変更して」の指示には含まれていなかったが、差し替えた内容が旧ストーリー4そのものを否定するため、要件を直さないと設計と矛盾する。このため requirements.md も合わせて更新した。

## 設計で決めたこと

- **認可の実体は既存の `User.role` のまま**とし、テキストファイルはその設定元にする。ログイン時に同期する方式にして、リクエストごとのファイルI/Oと、`IsAdminRole` を使う既存コードの作り直しを避けた。
- **`set_admin` コマンドは削除**し、`sync_admins`（ファイルの内容を既存の全ユーザーに反映）に置き換える。設定元が2つある状態を作らないため。
- ファイルの形式は1行1メールアドレス、空行と `#` のコメントを許容、大文字・小文字と前後の空白を無視。`backend/.gitignore` に追加してコミットしない。
- 管理者は上限の対象外だが、`UsageRecord` への記録は継続する（費用の把握のため）。画面では割合の代わりに「制限なし」と表示する。

## 補足

- 未解決事項を入れ替えた。旧「上限5倍の費用の見込み」を落とし、「ファイルの変更を既ログイン中のユーザーへ即時反映する必要があるか」「ファイルの配置場所（インフラ決定待ち）」を追加した。
- 上限の5倍化はコードには未反映だったため、コード側の差し戻しは発生していない。
- 実装はまだ行っていない。
