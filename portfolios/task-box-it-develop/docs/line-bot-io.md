# LINE BOT の入出力の対応

LINE BOTサーバー（`line_bot/`）が、**どの入力に対して何を返すか**の一覧。セットアップ・環境変数・アーキテクチャは [line-bot.md](line-bot.md)、仕様は [.kiro/specs/line-bot-server/](../.kiro/specs/line-bot-server/requirements.md) を参照。

返信の文言はすべて `line_bot/app/messages.py` にある。この文書の文言は2026-09-20時点のコードの値で、文言を変えたときはこの文書も合わせて直すこと。

## 全体の流れ

```
LINE → POST /webhook → 署名の検証 → イベントの取り出し → 重複の排除
        → （契約者の対話なら、待機メッセージを reply）→ ジョブに登録 → 200 を返す
                                                          ↓
                                          worker が1イベントを処理して、1通返す
```

- Webhookの応答は、処理の結果にかかわらず常に `200`（署名の不一致とJSONの不正だけ `400`）。依頼者への返信は、LINEのメッセージとして別に送られる。
- 返信は1イベントにつき1通。例外は契約者との対話で、待機メッセージ（reply）と回答（Push）の2通になる。
- すべての返信に、3つのクイックリプライ（後述）が付く。

## 1. ユーザーの操作と返信

判定は上から順に行われ、最初に当てはまった行の返信になる。

### ボタン（クイックリプライ）を押したとき

すべての返信の下に出るボタン。押すと postback の `data` が送られ、その固定値で機能を判定する（メッセージの文字列では判定しない）。登録・契約の有無は問わない。

| ボタン | `data` | 条件 | 返信 |
| --- | --- | --- | --- |
| ユーザー情報の登録 | `action=register` | `LIFF_ID` が設定済み | 下のページからご登録ください。<br>`https://liff.line.me/<LIFF_ID>` |
| 〃 | 〃 | `LIFF_ID` が未設定 | 次の形式でメッセージを送ってください。<br><br>【ユーザー情報の登録】<br>名前: 山田太郎<br>メールアドレス: taro@example.com |
| 面談予定日の調整 | `action=meeting` | 常に | 機能改修中です。準備ができましたらお知らせします。 |
| 契約する | `action=contract` | `CONTRACT_PAGE_URL` が設定済み | こちらのページからお手続きください。<br>`<CONTRACT_PAGE_URL>` |
| 〃 | 〃 | `CONTRACT_PAGE_URL` が未設定 | 機能改修中です。準備ができましたらお知らせします。 |
| （上記以外の `data`） | — | — | 返信しない |

### テキストを送ったとき

| # | 入力 | 条件 | 返信 | 送り方 |
| --- | --- | --- | --- | --- |
| 1 | `【ユーザー情報の登録】` で始まるテキスト | 形式・内容が正しい | 登録完了しました。ありがとうございます。 | reply |
| 2 | 〃 | 正しくない | `<理由>`<br><br>次の形式でお送りください。<br><br>【ユーザー情報の登録】<br>名前: 山田太郎<br>メールアドレス: taro@example.com<br>（理由は「登録のテキストの検証」を参照） | reply |
| 3 | それ以外のテキスト | 未登録のユーザー | 契約者でない場合、対話できません。下のボタンからお選びください。<br>はじめに、お名前とメールアドレスの登録をお願いします。 | reply |
| 4 | 〃 | 登録済みだが未契約 | 契約者でない場合、対話できません。下のボタンからお選びください。 | reply |
| 5 | 〃 | 契約者 | ① しばらくお待ちください。<br>② 対話の回答（次の表） | ① reply<br>② Push |

- 登録のテキスト（#1・#2）は、登録・契約の有無にかかわらず受け付ける。登録済みのユーザーが送ると、名前とメールアドレスを上書きする（契約状態は変えない）。
- 契約者かどうかは `users.contract_status` が `active` かで決まる。変更できるのは `python -m app.cli set_contract` だけ。

### 契約者との対話の回答（#5 の②）

上から順に判定する。

| 条件 | 回答 | LLMの呼び出し | 回数に数える | 履歴に保存 |
| --- | --- | --- | --- | --- |
| 処理を待つ間に契約者でなくなった | 契約者でない場合、対話できません。下のボタンからお選びください。 | しない | しない | しない |
| 今日の呼び出し回数が上限（`DAILY_LLM_CALL_LIMIT`、既定値30）に達している | 今日はたくさんお話ししたので、ここまでにさせてください。明日になるとまた使えます。 | しない | しない | しない |
| 対話プロンプト（`DIALOGUE_PROMPT_FILE`）が無い・空 | メッセージを受け取りました。担当者が確認しますので、少々お待ちください。 | しない | **する** | **する** |
| LLMの呼び出しに失敗、または回答が空 | エラーになりました。少し待ってから、もう一度送ってください。 | する | **する** | しない |
| 入力またはLLMの回答に、お金の話が含まれる（後述） | お金のお話は、こちらではお答えできません。別のページでご案内します。<br>`<CONTRACT_PAGE_URL>`（設定済みの場合のみ） | する | する | する（この案内文を回答として保存） |
| 上記以外 | LLMの回答を整形したもの（後述） | する | する | する |

**現状は `line_bot/prompts/dialogue.md` が空のため、契約者との対話はすべて3行目の仮の応答になる。** プロンプトを書くと、設定を変えなくてもLLMの回答に切り替わる。

- **お金の話の判定**: 入力か回答のどちらかが、`数字 +（円 / 万 / 千）`、または「見積」「費用」「お値段」「料金」を含む場合。プロンプトの指示だけに頼らず、送信前に機械的に判定している。
- **回答の整形**: 行頭の箇条書き・見出し・引用の記号と、`` ` `` `*` `_` `~` を取り除き、連続する空行を1つにまとめる。200文字を超える場合は、先頭200文字の後半（100文字目以降）にある文の区切りで切る。区切りは「。」→「！」→「？」→改行の順に探し、最初に見つかった種類の、最後の位置で切る。どれも見つからなければ200文字で切る。
- **LLMに渡す履歴**: そのユーザー自身の直近 `HISTORY_MAX_TURNS`（既定値10）往復。超えた分は保存時に古いものから消す。保存した履歴は `purge` で24時間後に消える。
- **上限の数え方**: 1ユーザー・1日（日本時間）の呼び出し回数。日付が変わると0から数え直す。

### 返信しない入力

| 入力 | 扱い |
| --- | --- |
| スタンプ・画像・動画・音声・位置情報・ファイルなど、テキスト以外のメッセージ | 無視する（返信しない） |
| 友だち追加（follow）・ブロック（unfollow）・グループへの招待など | 無視する。友だち追加時の案内は LINE Official Account Manager の「あいさつメッセージ」で設定する |
| `webhookEventId` または `source.userId` が無いイベント | 無視する |
| 同じ `webhookEventId` の再送 | 2回目以降は処理しない（返信しない） |
| ブロック済みのユーザーへの送信（LINEが `403` を返す） | 送信をやめて記録するだけで、再試行しない |

## 2. 登録のテキストの検証

1行目が `【ユーザー情報の登録】` で始まり、2行目以降に `名前: ...` と `メールアドレス: ...` がある（コロンは半角・全角のどちらでもよく、行の順序は問わない）。

| 検証 | 理由として返す文言 |
| --- | --- |
| `名前` または `メールアドレス` の行が無い | 形式が違います。 |
| 名前が空 | お名前が入っていません。 |
| 名前が50文字を超える | お名前が長すぎます（50文字まで）。 |
| メールアドレスが254文字を超える、または `xxx@yyy.zzz` の形でない | メールアドレスの形式が正しくありません。 |

LIFFの登録フォーム（次の章）も、同じ検証を通る。

## 3. HTTPのエンドポイント

| メソッド・パス | 入力 | 出力 |
| --- | --- | --- |
| `POST /webhook` | LINEからのWebhook（`X-Line-Signature` ヘッダ + JSON） | 署名が不一致・ヘッダなし → `400`（本文なし）<br>JSONとして読めない → `400`<br>それ以外 → `200`（本文なし。個々のイベントの結果は含めない） |
| `GET /liff` | なし | `LIFF_ID` が設定済み → 登録フォームのHTML（`200`）<br>未設定 → `<p>準備中です。</p>`（`404`） |
| `POST /liff/register` | `{id_token, name, email}` | 下の表 |
| `GET /healthz` | なし | DBとRedisの両方に疎通 → `200` `{"ok": true, "db": true, "redis": true}`<br>どちらかが不通 → `503`（不通の側が `false`） |

**`POST /liff/register` の応答**（本文は `{"message": "..."}`。フォームがそのまま画面に表示する）

| 条件 | ステータス | `message` |
| --- | --- | --- |
| `id_token` が無い | `400` | もう一度お試しください。 |
| IDトークンの検証に失敗 | `401` | もう一度お試しください。 |
| 名前・メールアドレスの検証に失敗 | `400` | 「登録のテキストの検証」の理由の文言 |
| 成功 | `200` | 登録完了しました。ありがとうございます。（フォームは1.5秒後に閉じる） |

LINEのユーザーIDは、リクエストの本文からは受け取らず、検証したIDトークンから取り出す。LIFFでの登録の完了は画面に表示されるだけで、LINEのメッセージは送らない。

## 4. 管理者のコマンド

| 入力 | 出力・効果 |
| --- | --- |
| `python -m app.cli set_contract <userId> active` | そのユーザーを契約者にする。以後、テキストを送ると対話になる |
| `python -m app.cli set_contract <userId> none` | 未契約に戻す。以後、テキストには「契約者でない場合、対話できません…」を返す |
| `python -m app.cli purge` | 保持期間を過ぎた会話履歴（24時間）と処理済みイベント（48時間）を消す |

未登録のユーザーIDを `set_contract` に渡すとエラーになる（先に登録してもらう）。

## 5. 気づいた点

入出力を整理する中で見つけた、仕様として意図したものか確認したほうがよい挙動。コードは変更していない。

- **お金の話と判定された場合も、LLMを呼んでから案内文に差し替えている。** 入力の側で判定できた時点でLLMを呼ばなければ、費用と待ち時間を減らせる。回答の側の判定は、LLMを呼んだ後でしかできない。
- **お金の話の判定が広い。** 「3万人が使う」「料金所」「2千件のデータ」のような、依頼の内容としての数字や言葉でも案内文に差し替わる。
- **仮の応答（プロンプトが空）でも、呼び出し回数を数え、履歴に保存している。** LLMを呼んでいないのに上限（1日30回）に達する。また、プロンプトを書いた後の最初の対話で、仮の応答が履歴としてLLMに渡る（24時間以内のもの）。
- **LLMが失敗した場合も回数に数えている。** 障害のあいだに再送を繰り返すと、回答を1度も得られないまま上限に達する。
- **空白だけのテキストを契約者が送った場合**、待機メッセージを返さずに、空の入力のままLLMの呼び出しまで進む（`is_dialogue` は空のテキストを対話とみなさないが、`handle_event` にはその分岐が無い）。
- **`messages.hearing_site_guide()` と `HEARING_SITE_URL` は、どの入力からも使われていない。** Webのヒアリングサイトへ案内する経路が、いまは無い。
- **ボタン以外の `data` の postback には何も返さない。** 将来リッチメニューなどで `data` を増やしたときに、無反応になって気づきにくい。
